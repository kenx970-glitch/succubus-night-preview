# Stripeテスト決済の接続と確認

ユーザーは「今回はStripe接続待ちで仕上げる」を選択しました。したがって、以下はキー設定後に実施する手順で、実Stripeで実施済みの記録ではありません。

## 接続

1. Stripe事業者にサービス内容を提示し、利用可否を確認します。サキュバスという題材だけで承認されたことにはなりません。露骨な性的コンテンツや性的満足を目的とするAIサービスはStripeの禁止・制限対象です。
2. テスト環境の秘密鍵を`.env`の`STRIPE_SECRET_KEY`に設定します。`sk_live_…`はコードで拒否します。
3. 公式Stripe CLIを用意し、別ターミナルで実行します。

```powershell
stripe listen --forward-to http://127.0.0.1:3210/api/webhooks/stripe
```

4. CLIが表示する署名秘密鍵を`STRIPE_WEBHOOK_SECRET`に設定してゲームサーバーを再起動します。Webhookはこのローカル経路に転送します。インターネットへのゲーム公開は不要です。
5. ローカルアカウントの月間上限を確認し、ウォレットから日本円税込価格を確認してCheckoutへ進みます。
6. Stripeの公式テストカードを使います。カード情報はStripeの画面にだけ入力します。

## 実接続後の受入チェック

- 500/1,500/3,000/5,000円でそれぞれ同額のSが付与される。
- 決済前、失敗、キャンセル、改ざんした戻りURLでSが増えない。
- 成功Webhook再送や履歴の再確認でSが二重付与されない。
- Checkout後にゲーム画面を閉じてもWebhookで付与され、再ログインで履歴を確認できる。
- 一時通信断後に同じ購入を再試行して同一Checkoutを取得する。古い未紐付け購入はStripeセッション一覧で照合し、存在しないことを確認して予約を解除する。
- G/S注文を明示選択し、残高と台帳が一度だけ更新される。
- Stripeテストダッシュボードから一部・全額返金し、返金成功時のみSが調整される。返金失敗への遷移も復元する。
- テスト異議申立てと勝訴・敗訴を確認する。Sの不足は負債として保持し、有償の購入・使用だけを凍結する。
- 他のアカウントの購入IDを指定しても閲覧・照合できない。

`stripe trigger checkout.session.completed`が作る任意のダミーイベントはゲーム内購入の照合情報を持ちません。S付与の受入確認はゲームから作ったCheckoutを使ってください。

## 実装上の境界

価格と通貨量はサーバーカタログを使います。署名は受信した生データで検証し、タイムスタンプ許容は300秒。StripeからCheckout/PaymentIntent/Charge/Refund/Disputeを再取得して照合します。受信InboxとイベントID、Checkout、PaymentIntent、操作キーで重複処理を防ぎます。再確認は30秒間隔および購入履歴から実行します。

支出上限は初期10,000円、設定0〜50,000円。**日本時間の購入開始月に、決済済み総額と未決済予約を計上する現在の仕様です。** 決済完了月への厳密な上限ではありません。返金で月の使用額を減らしません。上限変更は既存Checkoutを取り消しません。月境界のCheckout失効・再予約や上限引き下げ時の扱いを本番要件として確定してから公開してください。

返金と異議申立てが同一決済に重なった場合は、現在の確定返金額と異議申立て保留額の大きい方をSから保留します。これは二重控除を避ける初期方針です。異なる部分に対する部分返金と複数紛争の厳密な充当、返金後の獲得特典取り扱いは、本番運用の会計・返金規約で確定する必要があります。

返金APIを誰でも実行できる画面は設けていません。実返金は運営者がStripe上で法令・規約に従って実施し、その結果をサーバーが同期します。
